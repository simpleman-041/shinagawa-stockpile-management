## 承認された方針

上記の要件・DB設計・APIを対象範囲に採用し、画面設計の不一致は要件・APIを優先する。
在庫一覧から対象の在庫詳細へ進み、対象倉庫・品目・保管場所・期限・現在庫・割当を確認して入庫／出庫を登録する。
同じ詳細画面に履歴の検索・ページ送りと、元記録を確認する取消操作を設ける。

日時はサーバー生成、担当者は事前登録一覧から選択する。任意理由を保持し、失敗時は入力を消さない。
履歴検索は対象在庫ID、区分、状態、登録日時の半開期間に限定する。倉庫・物品名の独自API検索は追加しない。
新しい倉庫・品目・場所・期限の在庫作成は既存の在庫登録から行う。

## 対象API

全パスの接頭辞は `/api/v1`。

| 操作 | メソッド・パス | 成功結果 |
| --- | --- | --- |
| 履歴検索 | GET /stock-movements | Movement配列・ページ情報、200 |
| 個別参照 | GET /stock-movements/{movement_id} | 元のMovement、200 |
| 入出庫登録 | POST /stocks/{stock_id}/movements | MovementResult、201、Location付き |
| 条件付き取消 | POST /stock-movements/{movement_id}/cancellation | 取消済みの元Movementと現在庫、200 |

## 実装順序と変更予定

1. `app/services/movements.py`：既存stocksの数量・参照・DTO処理と共通DBトランザクションを使い、履歴取得・登録・取消を実装する。
2. `app/routes/movements.py`：既存在庫APIの入力・エラー処理を共用し、上記4操作を接続する。
3. `app/__init__.py`、`app/routes/demand_groups.py`：Blueprint登録と入出庫パスの404・405応答だけを追加する。DB接続・スキーマ・依存関係は変更しない。
4. `app/templates/stocks.html`、`app/static/js/stocks.js`、必要に応じて`app/static/css/stocks.css`：詳細画面に登録・履歴検索・取消確認を追加する。
5. `tests/test_movements.py`：承認済み方針に対するAPI・DB・サービスの検証を追加し、既存テストを回帰確認する。

画面ルート追加・他マスター画面変更・割当編集・容量集計・計算結果更新・認証追加・担当者管理・スキーマ変更は対象外。
通常の入出庫成功後は現在庫と履歴を再取得する。未実装の隣接APIに依存する表示は追加しない。

## 受入条件と検証計画

| 条件 | 確認方法 |
| --- | --- |
| 入庫・出庫で数量と担当者名写し付き履歴を一括保存 | Flaskクライアント、実SQLite、サービス直接呼出し |

| 終了品目への入庫を拒否し、出庫・条件を満たす取消を許可 | 品目終了前後の登録・取消とDB不変確認 |
| 元取引の本体を保持し、取消情報だけ追記、二重取消拒否 | 取消前後の全列比較、履歴件数・ID維持 |
| 削除・統合元、統合先旧世代の取消拒否、統合後新取引は取消可能 | 既存削除・統合APIと連携して確認 |

| 不正JSON、未知キー、日時投稿、重複クエリー、404・405 | ステータス・JSON構造・Allow・拒否時DB不変 |
