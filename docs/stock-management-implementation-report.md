# 在庫管理の実装・受入確認

2026年11月12日（JST）

## 採用範囲と仕様

本会話で依頼者が承認した、一覧・検索・登録・詳細・保管場所編集・期限訂正・論理削除／復元・確認付き統合を実装した。
要件書2.0、DB設計2026-11-01、API設計1.0と同日版DDLを採用した。
要件書・DB設計・DDLのSHA-256はAPI設計§1.1と一致し、実行用DDLも同一である。
主な対応はF03・F10・F11、Q28〜31・38〜43、P01・P06、U03、DBのTX01・TX03・TX04・TX07。

画面設計S003・S003-1〜3のロット番号、数量直接編集、検索項目を要件・API契約へ合わせる方針について、依頼者から「この方針で進める」と承認を得た。
登録後は保存完了メッセージ付き詳細へ遷移し、入力エラーはフォーム上に理由を表示する。
通常の入出庫・取消画面は次の機能範囲である。今回の登録時初期数量は入庫履歴と一括保存する。

## 入口と変更ファイル

倉庫・品目・避難所一覧の「在庫管理へ」から `/stocks` を開く。
新規登録は `/stocks/new`、詳細は `/stocks/{stock_id}`。

### 倉庫別の導線修正

依頼者から倉庫との対応が画面上で分かりにくいとの指摘を受け、倉庫一覧の各行に「在庫を見る」を追加した。
`/stocks?warehouse_id={warehouse_id}` へ移り、該当倉庫の在庫を表示する。
ページ見出しは倉庫名・倉庫IDを表示し、在庫登録へ進むとその倉庫を初期選択する。
登録画面のキャンセルと詳細画面の「この倉庫の在庫へ」も対象倉庫の一覧へ戻る。
倉庫一覧上部は「全倉庫の在庫を見る」と表示する。

## ブラウザ確認待ち

WindowsのMicrosoft Edgeで確認を試みたが、computer-useが現在のブラウザURLを十分に判定できず停止した。
ページの表示・操作、空状態、重要な拒否、通信失敗のブラウザ確認は未実行。自動テストのみで画面受入完了とは扱わない。

検証用DBに事前登録職員・倉庫・品目を用意し、次を確認する。

1. 在庫一覧を開き、空結果・検索・条件クリア・ページ送りを確認する。
2. 数量0、期限未確認で登録し、保存完了表示と詳細を確認する。
3. 分割不可品目へ0.5を入力し、拒否理由と入力保持を確認する。正の数量は担当者を選択して登録する。
4. 同一条件で再登録し、既存在庫へ加算されることを確認する。未確認期限では別行となることも確認する。
5. 場所と期限を訂正し、期限変更履歴を確認する。同じ期限の再保存では拒否理由を確認する。
6. 確認チェックと担当者を指定して論理削除する。削除済み検索から開き、現在の倉庫区分・全対応先を表示して復元する。
7. 別の場所で作った在庫を同じ場所へ訂正し、元・先を選んで統合プレビューの数量・状態・取消制限を確認して確定する。
8. 開発者ツールで通信を遮断して保存し、通信失敗表示と入力保持を確認する。復旧後に現在値を照合する。

統合トークンはAPI契約どおりアプリプロセス内で保管する。再起動で失われた場合は再プレビューが必要。
人間による独立したレビューとブラウザ受入確認が残るため、本機能の状態は「実装済み・画面検証待ち」とする。
