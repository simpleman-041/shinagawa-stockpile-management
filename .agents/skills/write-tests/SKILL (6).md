# pytestによる検証

ルートの`AGENTS.md`に従う。実装を追認するテストではなく、承認済み仕様に対する検証を作る。

## 必要な入力

- 対象機能・差分・受入条件、承認済み詳細要件、必要なAPI・DB・画面設計と版。
- 対象のservices・routes・接続処理、既存テストとfixture、承認済みDDL。
- Python・pytest・依存関係の実際の導入状況、アプリ生成方法、検証DBへの切替方法。

## 作業順序

1. **実行可能性を確認する。** 依存関係、Python環境、テスト構成、アプリ入口を調べる。2026-11-03調査時点ではpytestはrequirements未登録、testsは配置用ファイルだけ。現在も同様なら導入担当・承認版と構築範囲を確認する。採用方針は承認済みでも、未知の依存関係や設定を一括追加しない。実行不能の理由を隠さない。
2. **期待結果を仕様から定める。** 要件IDまたは該当節、入力・前提状態、操作、応答と最終状態を対応させる。仕様にない丸め式、期限境界、エラーコード等は人間に確認し、実装の返り値を期待値へコピーしない。期待値を実装と同じ計算関数で作らない。
3. **ケースを選ぶ。** 正常系・境界値・重要異常系を優先し、無関係な全組合せや一律のカバレッジ目標を増やさない。数量0・上限・超過、欠落・null・型違い、不在ID、削除済み・統合元、期限境界、割当超過、計算不可、保存失敗等から該当要件のケースを選ぶ。再発し得る既存不具合は回帰ケースにする。
4. **隔離データを用意する。** 最小限の架空データをfixtureで作る。DBは`tmp_path`等のテスト専用一時領域に作り、アプリが実際にそのDBだけを使うことを処理前に確認する。切替できなければ更新テストを実行しない。承認済みDDLと同じ制約・トリガーを使い、FKも有効にする。都合のよい簡略スキーマで代替しない。
5. **独立性と後片付けを確保する。** ケースごとに初期状態を分離し、順序や他担当のローカルDBに依存させない。接続・カーソル等を例外時も解放する。`:memory:`は接続ごとに別DBとなる点を確認し、別接続テストは同じ一時ファイルを使う。アプリがcommitする処理をfixtureの外側rollbackだけで隔離できると仮定しない。
6. **単体・API・DBを検証する。**
   - servicesの業務ロジックはHTTPなしで検証し、必要なDB依存は隔離DBを使う。業務上の期待結果をモックで消さない。
   - Flaskテストクライアントで承認済みメソッド・パス、ステータス、Content-Type、JSON構造・型、更新結果、重要なエラー・権限を確認する。実サーバー起動を必須にしない。アプリ生成方法は既存構成を使う。
   - DBでは負数・割当超過・不正統合・二重計上・履歴破壊の拒否と、途中失敗時の全関連データ不変を確認する。対象集計はJOINによる件数増幅も確認する。FKは設定値だけでなく不正参照の拒否も確認する。
   - 日付・時刻は基準を固定し、承認済みタイムゾーンと境界を扱う。競合が重要なら独立接続で検証する。DB操作をモックしたテストだけで原子性・制約を検証済みとしない。
7. **実行して調べる。** pytestと対象が実在し実行可能になったら、ルートで`python -m pytest`または実在する対象パスを指定して実行する。これは採用する実行方法であり、構築済みコマンドではない。関連ケースから実行し、影響する既存テストへ広げる。収集件数も確認し、0件を成功扱いしない。
8. **失敗を分類する。** 実装不具合、仕様不明、テスト誤り、環境障害を区別する。期待値変更は仕様根拠が確認できるテスト誤りに限り、根拠を報告する。失敗を隠す削除・skip・xfailや検証条件の弱体化をしない。修正依頼の範囲を超える場合は報告する。

## 完了条件と報告

関連仕様を検証するテストを用意し、実行可能なものを実行し、失敗原因と未検証範囲を明らかにする。失敗や必要確認の未実行があれば機能の実装完了を保証しない。テスト作成だけの依頼なら、作成済みと実行済みを分ける。

報告には次を含める。

- 対象要件と期待結果の根拠、追加・変更テスト、主な正常・境界・異常・回帰ケース。
- 実行環境、作業ディレクトリ、実行コマンド、成功・失敗・エラー・スキップ件数。実際の出力だけに基づく。
- 未実行・対象外と理由、失敗原因、人間や別担当に必要な対応。
- 画面確認も依頼された場合は手動操作の結果を別記する。APIテストでブラウザ操作まで確認したとしない。
