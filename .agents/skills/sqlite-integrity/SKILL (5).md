# SQLiteと業務整合性

ルートの`AGENTS.md`に従う。業務条件は承認済み詳細要件から読み、ここにある重点観点だけで例外や詳細条件を補完しない。

## 必要な入力

- `local-specs/`の承認済み詳細要件、DB設計・テーブル定義・ER図、承認済みDDLと版。
- 現行スキーマ、接続・初期化・トランザクション実装、呼出元、対象操作とデータ保全条件。
- Pythonと組込みSQLiteの実バージョン、接続設定、検証専用DB。実データを検証用に流用しない。

## 作業順序

1. **構造を照合する。** 設計書・DDL・現行DBのテーブル、列、型、PK・FK、UNIQUE・CHECK・NOT NULL・DEFAULT、インデックス、トリガーを比較する。必要時は`PRAGMA table_info`、`foreign_key_list`、`index_list`等で読み取り確認する。名前や制約を推測せず、差異があっても自動修復しない。
2. **不変条件を抽出する。** 要件と対応させ、正常時の遷移と拒否時に変化させないデータを列挙する。次表は照合観点であり、具体的条件の代用ではない。

   | 対象 | 要件から確定する内容 |
   | --- | --- |
   | 在庫・入出庫・取消 | 数量の型・単位・範囲、負数防止、出庫後の割当整合、取消条件 |
   | 割当・倉庫対応 | 在庫単位の割当合計、超過防止、専用・共有の区別、避難所対応と変更時の扱い |
   | 統合 | 保管場所を含む一致条件、期限状態、割当残、統合元参照、取消制限、二重計上防止 |
   | 削除・復元 | 論理削除と物理削除、集計除外、復元条件、関連参照の保持 |
   | 期限 | 状態、日付と判定時刻・タイムゾーン、当日境界、未確認・期限切れの用途別の扱い |
   | 充足・容量 | 算入対象、倉庫区分と割当による算入条件、換算・数値の保存表現・丸め順序、計算不可と在庫0の区別、期限切れ現物の容量への扱い |
   | 保存結果 | 保存範囲、当時の条件・参照名・警告、計算日時と保存日時、訂正元参照、編集・削除・上書き・再計算による履歴破壊の防止 |

3. **接続を安全に扱う。** 共通接続経路を使う。各接続でトランザクション外にて`PRAGMA foreign_keys = ON`を設定し、`PRAGMA foreign_keys`が1であることを確認してから業務処理へ渡す。有効化できなければ更新を進めない。Pythonのautocommit・isolation_levelにより接続直後もトランザクションが開く場合があるため、実際の状態を確認する。途中の設定で効いたとみなさない。
4. **安全なSQLを使う。** 値はプレースホルダーでバインドし、文字列連結やf文字列で埋め込まない。列名・並び順等は入力を直接SQLにせず、承認済み候補から許可する。不要な`INSERT OR REPLACE`等で削除・再作成や履歴喪失を起こさない。
5. **操作を原子的にする。** 在庫・割当・履歴等の関連更新と最新状態に依存する検証を、同一接続・同一トランザクションで行う。最外層にcommit・rollback責任を集約し、補助関数で途中commitしない。Pythonの版と既存制御に合わせ、明示BEGINと暗黙トランザクションを無計画に混在させない。`executescript`の暗黙commit等で境界を破らない。
6. **競合と失敗を扱う。** 別更新が入っても不変条件を破らないよう、承認済み制約と適切なトランザクション・条件付き更新等を組み合わせ、更新件数も確認する。単一書込だから安全と決めつけない。制約違反、ロック、途中例外、commit失敗では全体をrollbackし、失敗を上位へ伝える。無条件再試行で重複入出庫等を起こさない。接続は確実に閉じる。接続のコンテキストマネージャーだけではcloseされない。
7. **構造変更を分離する。** 列・制約・インデックス・トリガー・初期化方法の変更には、理由、影響、移行案、既存データと履歴の保全、復旧方法を提示し、人間の承認を得る。承認済み変更はCONTRIBUTINGに従いSQL等で共有し、独自DDLや起動時の破壊的初期化で代替しない。
8. **整合性を検証する。** `write-tests`で承認済みDDLの隔離DBを使い、正常系、重要拒否、更新・保存途中の失敗、必要範囲の別接続競合を確認する。失敗後の全関連データが操作前と一致すること、履歴不変、FK有効化を検証する。`PRAGMA foreign_key_check`も必要時に使い、通過だけで数量・集計・業務整合性を保証したとしない。

## 判断に迷う場合

在庫を減らすため割当を自動削減する、統合条件を緩める、履歴を上書きする等の簡略化をしない。必要資料がない、仕様と制約が矛盾する場合はAGENTS.mdの確認形式を使い、該当更新・集計の確定実装を保留する。

## 完了条件と報告

対象の不変条件、接続ごとのFK、原子性、失敗時の不変、関連テストを確認し、AGENTS.mdの実装完了条件を満たすこと。

要件とDB設計・DDLの版、対象テーブルと操作、トランザクション境界、FK確認と検証結果、データ・履歴への影響、承認事項、未解決・未実行範囲を報告する。DBファイルや実データは添付しない。

技術参照は[Python sqlite3](https://docs.python.org/3/library/sqlite3.html)と[SQLite外部キー仕様](https://www.sqlite.org/foreignkeys.html)。実環境に対応する版を確認する。
