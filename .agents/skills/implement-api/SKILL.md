# Flask JSON APIの実装

ルートの`AGENTS.md`に従う。機能全体は`implement-feature`、DB処理は`sqlite-integrity`、テスト作成・実行は`write-tests`の担当とする。

## 必要な入力

- `local-specs/`の承認済みAPI設計、関連する詳細要件・DB・画面設計と各版。
- 既存ルートと登録方法、利用するJavaScript、services、共通JSON・エラー処理、認証・認可方式、関連テスト。
- 対象操作と承認範囲。設計書の名称・場所やURLプレフィックスを推測しない。

## 作業順序

1. **既存境界を確認する。** 画面ルートとJSON APIを識別し、パス・メソッドの重複、呼出元、登録方法を調べる。Blueprintやアプリ生成関数が既にあると仮定しない。共通入口が未実装なら担当と構成を確認する。
2. **契約を照合する。** 下表の適用項目について、承認済み資料と現行実装・利用側を比較する。対象外は理由を示す。

   | 項目 | 確認内容 |
   | --- | --- |
   | 操作 | パス、HTTPメソッド、画面・要件との対応 |
   | 入力 | パス・クエリ・JSON、Content-Type、項目名、型、必須、null、範囲、日付・数量・単位の表現 |
   | 一覧 | 適用する場合の検索・並び順・ページングと空結果 |
   | 成功 | ステータス、JSON構造、各項目の型、本文の有無 |
   | 失敗 | 不正JSON、型・業務条件違反、対象なし、状態競合、認証・認可失敗、内部障害の応答 |
   | 保護 | 認証要否、操作権限、セッションとCSRF対策、公開範囲 |
   | 更新 | 更新対象、原子性、再送時の扱い、競合時の挙動 |

3. **未確定契約を確認する。** 不足する項目、根拠、影響する利用側、推奨案と主な代替案を示して人間に判断を求める。REST慣習やFlask既定動作を理由に契約を確定しない。承認までは該当APIの確定実装・テスト期待値の固定を行わない。
4. **HTTP境界を実装する。** 読取操作を適切なメソッドで扱い、GETで状態を変更しない。承認済みの成功・失敗ステータスを返す。失敗を成功ステータスで隠さず、本文を持たない応答にJSONを付けない。400・401・403・404・409・415・422等の採用は契約で確認し、一律に決めない。
5. **入力と権限を検証する。** JSON構文、トップレベルの型、項目の型・必須・null・範囲・未知項目を契約に従い検証する。数量の文字列・小数・真偽値を整数へ黙って変換しない。URLのIDやブラウザ表示を信頼せず、サーバーで存在と操作権限を確認する。必要な認証・認可仕様が不明なら該当処理を保留する。
6. **servicesへ委譲する。** routesは入力解析・HTTP境界の検証・サービス呼出し・応答変換に限定する。業務条件と計算はservicesへ置く。DB連携時は`sqlite-integrity`を適用し、処理途中で別接続や個別commitを増やさない。
7. **エラーを一貫して返す。** 業務上の拒否と想定外障害を分け、承認済みJSON構造へ変換する。既定HTMLエラーがAPIへ漏れないか調べ、404・405やJSON解析失敗も契約に照合する。共通ハンドラー変更では画面ルートへの影響も確認する。内部例外・SQL・秘密情報を返さず、rollback後に失敗を応答する。ログも機密を除く。
8. **APIを検証する。** `write-tests`でFlaskテストクライアントを用い、メソッド、ステータス、Content-Type、JSON項目・型、状態変化を確認する。不正JSON、必須欠落、型・境界違反、不在ID、重要な業務拒否・権限違反を対象にする。拒否時のDB不変、画面側の呼出し互換性も確認する。対象外の認証等を実装済み扱いしない。

## 完了条件と報告

対象契約が承認済みで、利用側の互換性と関連テストを確認し、AGENTS.mdの実装完了条件を満たすこと。

対象パス・メソッド、契約出典と版、変更ファイル、互換性・権限・DBへの影響、検証結果、未確定項目と未実行理由を報告する。承認済み契約変更は変更点と承認根拠も示す。
